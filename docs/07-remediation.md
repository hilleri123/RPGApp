# План исправлений

Сквозной приоритизированный план по всем найденным дефектам. Описания самих дефектов — в [04-issues-backend.md](04-issues-backend.md), [05-issues-frontend.md](05-issues-frontend.md), [06-issues-infra.md](06-issues-infra.md).

## Принцип приоритизации

Волны упорядочены по **необратимости ущерба**, а не по сложности:

1. Что портит или раскрывает данные пользователей — первым.
2. Что делает состояние системы неконсистентным — вторым.
3. Что нарушает разграничение прав — третьим.
4. Что мешает нормально эксплуатировать — четвёртым.
5. Что раздражает пользователя — пятым.

Внутри волны порядок свободный, но `BE-01` стоит делать самым первым: это единственный дефект, который **портит уже существующие данные**, и чем дольше он живёт, тем больше поломанных сценариев придётся чинить руками.

| ID | Что сделали | Статус |
|----|-------------|--------|
| `BE-01` | Фильтр по `scenario_id` при персисте сущностей | готово |
| `BE-03` | Проверка `is_master` в `DELETE /session/{id}` | готово |

| `BE-05` | Убран `user = None` в `list_sessions` | готово |
| `BE-14` | Единый `SECRET_KEY`, отказ старта в проде | готово |
| `BE-17` | `except ValueError` вместо `except Exception` | готово попутно |
| `FE-01` | base64url и явная проверка `exp` в middleware | готово |

**Критерии приёмки и что получилось:**

- Пользователь из сценария A не может изменить сущность сценария B — закрыто тестами `test_persist_filters_by_scenario_id` и `test_persist_ignores_entities_of_another_scenario`.
- Не-мастер получает 403 на `DELETE /session/{id}` — `test_delete_session_rejects_non_master`.
- `GET /session/{id}` — роут удалён, проверяется `test_get_session_by_id_route_is_gone`.
- Аноним получает 401 на `POST /rulesystems/reload` — проверено тестом и живым запросом.
- `list_sessions` возвращает только сессии пользователя — `test_list_sessions_filters_by_user`.
- Приложение не стартует в проде с дефолтным **или пустым** `SECRET_KEY`.
- `isTokenExpired` корректно разбирает base64url и считает токен без `exp` невалидным — проверено вручную, автотеста нет (нет тест-раннера, `INF-06`).

Регрессионные тесты: [RPGdata/tests/test_wave1_security.py](../RPGdata/tests/test_wave1_security.py), 13 тестов. Каждый проверен на откате своей правки — падает именно соответствующий тест. Полный набор: 96 passed против 83 до волны.

**Чего не удалось сделать так, как планировалось.** Предполагалось начать с минимального `conftest.py` (`INF-06`), но `httpx` не установлен в образе, поэтому `TestClient` недоступен. Тесты пришлось построить на интроспекции `app.routes`, вызове обработчиков напрямую и фейковой сессии БД. Это работает, но проверок уровня HTTP по-прежнему нет.

## Волна 2. Консистентность рантайма

Дефекты, из-за которых система по-разному отвечает на одинаковые запросы. Их тяжело диагностировать в проде, потому что воспроизводятся они непредсказуемо.

| ID | Что делаем | Оценка |
|----|-----------|--------|
| `BE-06` | Все REST-роуты через `ensure_manager` | ~2 ч |
| `BE-15` | Персист остальных сущностей или явная ошибка | ~4 ч |
| `BE-16` | Блокировка вокруг read-modify-write действий | ~4 ч |
| `BE-07` | Зафиксировать «один воркер» или Redis pub/sub для кеша | ~1 ч / ~1 д |
| `FE-03` | Очередь исходящих действий с переотправкой | ~1 д |
| `FE-06` | Вызывать `removeSession` при выходе и завершении | ~1 ч |

**Готово, когда:**

- Тест: REST и WebSocket для одной сессии видят одно состояние (один ключ Redis).
- Тест: `set_field("locations", ...)` либо сохраняет, либо бросает — но не молчит.
- Тест: два параллельных `submit_action` не теряют друг друга.
- Ограничение по воркерам либо снято, либо явно записано в `compose.prod.yml` и документации.
- Ручная проверка: действие, отправленное при разорванном сокете, доходит после переподключения ровно один раз.

`BE-07` намеренно даёт вилку оценки. Дешёвый вариант — честно зафиксировать однопроцессный запуск; полноценный — общая инвалидация кеша. Второй имеет смысл только если масштабирование реально планируется.

## Что стоит сделать до следующих волн

Приоритет теперь у тестовой инфраструктуры, и это стало очевиднее после волны 1.

| ID | Что делаем | Оценка |
|----|-----------|--------|
| `INF-09` | Изоляция состояния между тестами | ~4 ч |
| `INF-06` | `httpx` в зависимостях, `conftest.py` с тестовой БД и HTTP-клиентом, smoke по роутам | ~1 нед |

`INF-09` идёт первым: пока полный прогон даёт два фоновых падения, набор не отвечает на вопрос «сломал ли я что-нибудь», и каждую волну приходится проверять откатом отдельных файлов. Волна 1 это уже показала на практике.

Показательно, что `BE-02` — эндпоинт, вызывающий несуществующий метод, — прожил в коде до статического анализа. Smoke-тест, обходящий все зарегистрированные роуты, пишется за час и поймал бы его сразу.
