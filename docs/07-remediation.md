# План исправлений

Сквозной приоритизированный план по всем найденным дефектам. Описания самих дефектов — в [04-issues-backend.md](04-issues-backend.md), [05-issues-frontend.md](05-issues-frontend.md), [06-issues-infra.md](06-issues-infra.md).

## Принцип приоритизации

Волны упорядочены по **необратимости ущерба**, а не по сложности:

1. Что портит или раскрывает данные пользователей — первым.
2. Что делает состояние системы неконсистентным — вторым.
3. Что нарушает разграничение прав — третьим.
4. Что мешает нормально эксплуатировать — четвёртым.
5. Что раздражает пользователя — пятым.

Внутри волны порядок свободный, но `BE-01` стоит делать самым первым: это единственный дефект, который **портит уже существующие данные**, и чем дольше он живёт, тем больше поломанных сценариев придётся чинить руками.

## Волна 1. Целостность и утечка данных

Пока это не закрыто, любую другую работу можно считать преждевременной.

| ID | Что делаем | Оценка |
|----|-----------|--------|
| `BE-01` | Фильтр по `scenario_id` при персисте сущностей | ~2 ч |
| `BE-03` | Проверка `is_master` в `DELETE /session/{id}` | ~15 мин |
| `BE-02` | Починить или удалить `GET /session/{id}` | ~1 ч |
| `BE-04` | Закрыть `POST /rulesystems/reload` | ~15 мин |
| `BE-05` | Убрать `user = None` в `list_sessions` | ~1 ч |
| `BE-14` | Единый `SECRET_KEY` из настроек, падение при дефолте | ~1 ч |
| `FE-01` | base64url и явная проверка `exp` в middleware | ~1 ч |

**Готово, когда:**

- Тест: пользователь из сценария A не может изменить сущность сценария B через рантайм сессии.
- Тест: не-мастер получает 403 на `DELETE /session/{id}`.
- Тест: `GET /session/{id}` отвечает 200 для участника (или роут удалён).
- Тест: аноним получает 401 на `POST /rulesystems/reload`.
- Тест: `list_sessions` возвращает только сессии пользователя.
- Приложение не стартует с дефолтным `SECRET_KEY`.
- Тест: `isTokenExpired` возвращает `true` для токена без `exp` и корректно разбирает base64url.

Половина этих проверок требует инфраструктуры тестов, которой нет (`INF-06`). Практично сделать минимальный `conftest.py` **в начале** этой волны — иначе исправления придётся принимать на веру.

## Волна 2. Консистентность рантайма

Дефекты, из-за которых система по-разному отвечает на одинаковые запросы. Их тяжело диагностировать в проде, потому что воспроизводятся они непредсказуемо.

| ID | Что делаем | Оценка |
|----|-----------|--------|
| `BE-06` | Все REST-роуты через `ensure_manager` | ~2 ч |
| `BE-15` | Персист остальных сущностей или явная ошибка | ~4 ч |
| `BE-16` | Блокировка вокруг read-modify-write действий | ~4 ч |
| `BE-07` | Зафиксировать «один воркер» или Redis pub/sub для кеша | ~1 ч / ~1 д |
| `FE-03` | Очередь исходящих действий с переотправкой | ~1 д |
| `FE-06` | Вызывать `removeSession` при выходе и завершении | ~1 ч |

**Готово, когда:**

- Тест: REST и WebSocket для одной сессии видят одно состояние (один ключ Redis).
- Тест: `set_field("locations", ...)` либо сохраняет, либо бросает — но не молчит.
- Тест: два параллельных `submit_action` не теряют друг друга.
- Ограничение по воркерам либо снято, либо явно записано в `compose.prod.yml` и документации.
- Ручная проверка: действие, отправленное при разорванном сокете, доходит после переподключения ровно один раз.

`BE-07` намеренно даёт вилку оценки. Дешёвый вариант — честно зафиксировать однопроцессный запуск; полноценный — общая инвалидация кеша. Второй имеет смысл только если масштабирование реально планируется.

## Волна 3. Разграничение прав

| ID | Что делаем | Оценка |
|----|-----------|--------|
| `BE-11` | `scenario_id` в `where` пяти роутов `locations.py` + общая зависимость | ~2 ч |
| `BE-10` | Аутентификация в `config_editor` | ~2 ч |
| `BE-08` | Закрыть `GET /rooms`, срок жизни кода комнаты | ~3 ч |
| `BE-09` | Приглашения или подтверждение входа в лобби | ~1 д |
| `FE-05` | Общий guard-компонент по ролям | ~3 ч |

**Готово, когда:**

- Тест-матрица «роль × эндпоинт» проходит для `locations`, `config_editor`, `observers`, `lobby`.
- Прямая ссылка на страницу админа или мастера без прав показывает экран «нет доступа», а не пустоту.

`BE-11` стоит делать через общую зависимость, а не пятью правками `where`: те же грабли иначе повторятся в следующем роуте. Полезно заодно проверить остальные сущности — паттерн «поиск по `id` без `scenario_id`» вероятен и вне `locations.py`.

## Что стоит сделать до всех волн

Одна вещь окупается немедленно и влияет на все остальные: **`conftest.py` с тестовой БД и HTTP-клиентом** (часть `INF-06`, ~1 день). Без него каждая волна проверяется вручную, а регрессии ловятся пользователями.

Показательно, что `BE-02` — эндпоинт, вызывающий несуществующий метод, — прожил в коде до статического анализа. Smoke-тест, обходящий все зарегистрированные роуты, пишется за час и поймал бы его сразу.
