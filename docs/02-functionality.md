# Функциональность

Что система реально умеет — по доменам. Технические детали реализации см. в [01-architecture.md](01-architecture.md).

## Роли

| Роль | Флаг / признак | Что может |
|------|----------------|-----------|
| Аноним | нет кук | Смотреть обсервер-комнату по коду, читать `/scenarios` |
| Пользователь | `access_token` | Лобби, заявки на персонажей, профиль, история бросков |
| Игрок | участник сессии | Всё выше + игровая сессия за своего персонажа |
| Мастер | `can_be_master` | Создание и ведение сценариев, запуск миров, ведение сессии |
| Админ | `is_admin` | Группы доступа, управление пользователями |

Роль в конкретной сессии определяется динамически: мастер — создатель, игрок — тот, у кого есть `character_id`.

## Подготовка сценария

Мастер создаёт сценарий, выбирает систему правил (`rule_id_str`) и наполняет его сущностями:

| Сущность | Назначение |
|----------|-----------|
| `story_beat` | Сюжетный элемент, узел повествования |
| `location` | Место; несёт карту, полигоны, вложенные локации |
| `npc` | Персонаж мастера |
| `game_item` | Предмет |
| `player_character` | Заготовка персонажа игрока |
| `note` | Заметка мастера |
| `counter` | Счётчик / трекер (часы, ресурсы) |
| `obstacle` | Препятствие |
| `scenario_todo` | Задача по подготовке сценария |

Форма редактирования каждой сущности **генерируется плагином**, а не захардкожена: бэкенд отдаёт JSON-схему через `editor_config`, фронтенд рендерит по ней поля. Поэтому у Dungeon World и Blades in the Dark разные наборы полей персонажа без изменения общего кода.

`scene_exposure` задаётся на `story_beat` и `location` — заранее описывает, что игроки увидят, когда мастер откроет эту сцену.

Дополнительно: пакеты сущностей (`entity_packs`) и наборы шаблонов (`template_sets`) для переиспользования между сценариями, генерация сущностей фабриками, загрузка изображений и аудио.

## Запуск мира и кампании

Сценарий из состояния «подготовка» переводится в **launched** — снимок мира, который живёт между игровыми встречами. Внутри launched-сценария проводятся отдельные подходы (сессии).

Кампания (`campaign`) объединяет подходы: между ними работает **carryover** — состояние персонажей, инвентарь и счётчики переносятся в следующий подход. Партии (`scenario_party`) группируют персонажей.

## Лобби

Точка сбора перед игрой. Мастер видит подключившихся, назначает персонажей, запускает сессию. Работает по своему WebSocket-каналу `/lobby/ws/{id}`, состояние — в Redis.

Лобби можно создать из Telegram-бота командой — бот дёргает RPC `create_lobby` и присылает ссылку.

## Игровая сессия

Основной режим. Мастер и игроки в одном WebSocket-канале, у каждого свой набор видимых полей.

**Сцены.** Мастер открывает сцену — игроки получают её описание и связанные сущности. Живые сцены хранятся в Redis, не в SQL.

**Карта и полигоны.** У локации есть изображение-карта и полигоны-области. Мастер управляет тем, какие полигоны раскрыты (`polygon_shown`) — так работает туман войны.

**Presented entity.** Мастер может «показать» игрокам конкретную сущность (NPC, предмет, локацию) — она выводится крупно у всех.

**Заметки и рассылки.** Личные заметки мастера, заметки для игроков, адресные рассылки (`dispatches`) конкретным игрокам и ответы на них (`message_replies`).

**Аудио.** Очередь треков (`audio_queue`), синхронное воспроизведение у всех участников.

**Таймлайн и логи.** Хронология событий сессии, доступная по ролям.

**Player seen.** Система отслеживает, что каждый игрок уже видел (`player_seen`), чтобы подсвечивать новое.

## Действия и броски

Действие — это не одноразовая команда, а **workflow с состоянием**, живущий в `actions`. Игрок или мастер запускает действие, оно проходит стадии, участники по очереди вносят вклад, в конце применяется эффект на мир.

Для Dungeon World основной workflow — `perform_move`:

1. Игрок объявляет ход и цель.
2. Добавляются бонусы, другие игроки могут помочь (`aid`).
3. Бросок костей.
4. По результату (`hit` / `partial` / `miss`) выбирается исход и его последствия.
5. Формируется манифест изменений, при необходимости бросается урон.
6. Изменения применяются к персонажам и миру.

Инициатор может **отменить** действие, пока не совершён бросок — политика в [action_cancel_policy.py](../RPGdata/app/services/action_cancel_policy.py). После броска отмена доступна только мастеру.

Все броски пишутся в `roll_record` и доступны в истории пользователя.

## Обсерверы

Режим «зрителя» для стрима или для тех, кто не играет. Мастер создаёт комнату с кодом, по ссылке `/observer/{code}` любой может смотреть **без регистрации**. Обсервер видит урезанный набор: локации, сцены, персонажей, полигоны, аудио, presented entity.

## Заявки на персонажей

Игрок подаёт заявку на участие с описанием персонажа; мастер видит очередь заявок в `/master/applications`, одобряет или отклоняет. При одобрении создаётся `player_character` и привязывается к игроку.

## Аутентификация и профиль

Вход: email + пароль, регистрация, magic-link по одноразовому токену, Telegram Mini App (валидация `initData` по HMAC).

Профиль: свои персонажи, история бросков, привязка Telegram, список доступных сценариев.

## Telegram-бот

Отдельный контейнер, общается с бэкендом по RabbitMQ RPC:

- `/link` — привязка Telegram-аккаунта: бот получает одноразовый токен и отдаёт ссылку для входа.
- Создание лобби и получение ссылки на него.

Бот принципиально не ходит в БД напрямую — вся логика на бэкенде.

## Администрирование

Группы доступа (`access_groups`) ограничивают, кто видит какие сценарии. Управление доступно пользователям с `is_admin`.

## Системы правил

| Плагин | Статус |
|--------|--------|
| PbtA (base) | Базовый слой, полностью работает |
| Dungeon World | Наиболее проработан: `perform_move`, урон, HP, инвентарь |
| Gumshoe (+ 3 варианта сеттинга) | Есть схемы сущностей, workflow слабее |
| Blades in the Dark | Каркас |
| Everyone is John | Каркас |
| I'm Bitter and I Keep Records | Каркас |

Практический вывод: продакшн-готовый путь — только Dungeon World. Остальные системы позволяют вести сценарий, но без глубокой механики действий.
